# Demo voice end-to-end tests

## Reusing browser mechanics

Voice suites use the local driver for navigation, observations, browser evaluation/snapshots, shared-audio hooks, protocol evidence, and bounded subprocess cleanup while keeping scenario setup and benchmark policy in the suite:

```ts
import { test } from './voice-test-fixture.ts';

test('voice scenario', async ({ page, voiceDriver }) => {
  await voiceDriver.navigate(process.env.MAELSTROM_BASE_URL);
  const before = voiceDriver.cursor();
  // Scenario-specific key setup and actions stay in the consumer.
  await page.getByRole('button', { name: 'Start voice' }).click();
  await voiceDriver.waitForObservation(
    (event) => event.type === 'voice-state',
    { after: before, timeoutMs: 10_000, signal: voiceDriver.signal },
  );
  const snapshot = await voiceDriver.snapshot();
  voiceDriver.assertHealthy('scenario setup');
});
```

Observations identify the run/page, carry monotonically increasing sequence numbers, and retain separate Node-monotonic and browser-performance clock domains. The bounded buffer exposes overflow and rejects expired cursors rather than silently skipping events. The Playwright fixture records evidence and disposes its browser instrumentation automatically; `navigate(baseURL, false)` skips AudioWorklet capture when unnecessary. Use `voiceDriver.startPlayback` or `voiceDriver.startProcess` for subprocesses that must be cancelled with the driver lifecycle; `dispose()` aborts managed processes and waits for cleanup, with termination escalating from SIGTERM to SIGKILL. The standalone `startVoiceProcess` has its own timeout; pass an explicit `signal` to tie it to lifecycle cancellation.

Run the standalone benchmark on Linux with `TTS2MIC_BIN` and `PULSE_SERVER` set (normally supplied by the voice-devtools container), using its separate Playwright configuration. The default full-scenario mode has no test retries; `VOICE_BENCHMARK_SINGLE_TURN=1` instead enables three retries:

```sh
bunx playwright test --config apps/demo/e2e/voice/playwright.benchmark.config.ts
```

The app must already be running; prepare the fixed WAV fixtures as for the voice E2E suite. Set `VOICE_BENCHMARK_REPETITIONS` to an integer from 1 to 3 (default `1`) to repeat the fixed scenarios explicitly. Recorder and test time limits scale to the requested repetitions. The JSON and exactly two complete session WAVs are attached to the Playwright run. Ordinary conversation tests likewise attach exactly two complete session WAVs: the actual captured microphone input and assistant-rendered output, aligned to the same 48 kHz frame timeline. Captured active-audio duration is threshold-based non-silence, not VAD-ground-truth speech duration. Turn boundaries use the voice UI returning to connected/listening plus one second of quiet monitor audio; pauses may still make a boundary ambiguous. Latency is reported per human VAD segment using two complete session WAV attachments on one 48 kHz browser AudioContext/AudioWorklet clock: the human track is the actual injected `getUserMedia` microphone track used by the app, and the assistant track is the actual WebRTC `MediaStream` assigned to the app `HTMLAudioElement`, routed through the shared graph and rendered exactly once before the physical speaker sink. Both WAVs have the same frame range and sample rate; latency sample offsets address these files. Assistant latency is browser-rendered, not physical-speaker loopback. Voice-devtools VAD runs on the captured input WAV with threshold `0.9` and zero boundary padding; t=0 is the first VAD sample. Human VAD segments separated by no more than 500 ms are grouped as one turn. Assistant onset uses a `0.01` sample threshold and merges sub-10 ms quiet gaps. Overlap, unanswered turns, missing blocks, and unaligned frames are unsupported. The PulseAudio monitor remains a separate active-audio measure. UI state and monitor silence orchestrate scenario completion only, not latency. Barge-in overlap, reliable transcript word count, and WPM remain unsupported.

From the workspace root, run `bunx nx run @maelstrom-co/demo:voice-e2e`. Its TypeScript runner prepares three speech fixtures, launches the serial Chromium voice scenarios in the voice-devtools container, collects the HTML report and diagnostics under `apps/demo/dist/docker-voice`, and opens `report/index.html` on macOS. The Nx target is uncached and non-parallel. Docker orchestration uses the installed Docker CLI through Node's `child_process` API, so no Docker SDK dependency is required; the runner preserves a failing test exit status after collecting and opening the report.

Run the dedicated containerized benchmark from the workspace root with `bunx nx run @maelstrom-co/demo:voice-benchmark`. It uses the same voice-devtools image and fixture preparation but selects `playwright.benchmark.config.ts`, including its deterministic shared-AudioWorklet capture test; it does not change the ordinary voice E2E suite. The benchmark verifies that the image exposes `tts2mic-mcp vad` before running VAD. The host collects Playwright's HTML report, benchmark JSON/WAV attachments, runner metadata, and Docker log under `apps/demo/dist/docker-voice/` (`report/index.html` and `benchmark-results/`). Prerequisites are Docker, a running reachable demo app, and the voice-devtools audio container's Linux/PulseAudio/TTS2MIC setup. The host prepares the three scenario WAV fixtures before launch; preparing the generated fixtures needs the configured TTS provider's credentials unless matching audio is already cached (for ElevenLabs, `ELEVENLABS_API_KEY` and optionally `ELEVENLABS_VOICE_ID`). Local mode defaults to `http://localhost:3000` and the configured WebSocket port; `MAELSTROM_HOST`, `MAELSTROM_APP_PORT`, and `MAELSTROM_WS_PORT` can configure host forwarding. For a BYOK target, provide `MAELSTROM_E2E_OPENAI_API_KEY` in the host shell; it is passed only into the benchmark container when present and is never printed by the runner. Set `VOICE_BENCHMARK_REPETITIONS` to 1–3 (default 1). Do not pass provider secrets such as `DEEPGRAM_API_KEY` to the audio container. Full-scenario benchmark retry count remains zero. Set `VOICE_BENCHMARK_SINGLE_TURN=1` in the host shell to opt into exactly one playback of the full `only-tasks.wav` human fixture and wait for that assistant response; this mode always reports one repetition and the selected scenario. Its fixture VAD preflight and captured input retain all raw VAD segments; multiple speech islands are treated as one logical command for this known single-playback fixture. The latency window spans the first raw VAD start through the last raw VAD end, and latency is measured from that final end only when assistant output does not overlap any part of the command. Empty VAD results, overlap, or ambiguous output leave latency unsupported. It does not trim audio or synthesize turn boundaries. Each single-turn attempt records expected and captured raw-VAD active milliseconds and their ratio; a ratio below 50% invalidates the attempt. This conservative coverage check is diagnostic rather than proof that identical speech content was captured. Unsupported latency caused by assistant onset before the final human VAD end or overlap also invalidates the attempt. Invalid attempts attach their sanitized report before failing, and single-turn mode alone gets three built-in Playwright retries (four total attempts with retry indices 0–3); the report's attempt index distinguishes each attempt. Persistent invalidity remains a failed test, never a reported latency. For example: `VOICE_BENCHMARK_SINGLE_TURN=1 bunx nx run @maelstrom-co/demo:voice-benchmark`. Without this flag, all three scenarios, existing repetition behavior, and zero retry behavior remain unchanged. In full-scenario mode, each fixture must produce at least 150ms of activity on the captured assistant WebRTC track or fail after 30 seconds. Before every next fixture, the runner continuously rechecks that assistant-only track and releases input only after its existing 1-second completion-quiet interval plus a 2-second post-speech buffer, and after the prior source-audio end-to-next-source-onset gap reaches 30 seconds. A resumed assistant burst resets the quiet/buffer wait; if one is detected during the `tts2mic` 3-second lead-in, playback is stopped and the attempt fails closed because the runner exposes no proof that source audio had not begun. The fixture is never replayed after an uncertain cancellation. The lead-in is included when scheduling source onset, not added to the 30-second gap. This pacing is not applied to the one-fixture single-turn diagnostic. The benchmark's active-audio duration and turn boundary are approximate; human-first-input latency, transcript word count, and WPM remain unsupported. A live measurement still requires a credentialed run against the configured app/provider; deterministic configuration tests do not provide live latency data.

### PR preview CI

Apply both `deploy-preview` and `bench-voice` to an open, same-repository PR. Deployment still requires fresh approval for its exact head SHA; `bench-voice` never authorizes deployment or future commits. Either label order works: successful deployment checks live labels, and adding `bench-voice` can benchmark an already approved/deployed head. Workflow and harness changes must first land on the default branch because GitHub enables `workflow_dispatch` only for workflows present there and trusted base-side code must handle secrets. After that, manually run **Deploy PR Preview** from the default branch with input `pr_number=<number>` to validate an already-deployed PR; both live labels and matching approved/deployed/head SHAs remain required. The application under test is still the approved PR head. The benchmark holds the same per-PR queue as deployment and teardown, validates the actual preview URL against the configured preview account, and rechecks labels, SHA and request ownership during execution. It runs trusted workflow-version benchmark tooling, not PR-controlled runner scripts. The approved PR application necessarily receives the BYOK OpenAI key, so only approve trusted revisions and use a dedicated restricted key.

Configure repository secrets `MAELSTROM_E2E_OPENAI_API_KEY` and `ELEVENLABS_API_KEY`; optionally set `ELEVENLABS_VOICE_ID`. The existing `CLOUDFLARE_PREVIEW_WORKERS_DEV_SUFFIX` variable identifies the preview account. The repository's Actions token needs pull access to `ghcr.io/maelstrom-co/voice-devtools:0.1.0`; the job requests `packages: read`. The job has no Cloudflare credentials and invokes the same standalone Bun/Docker runner as the Nx target without installing the PR workspace. It performs one full-scenario repetition with zero retries; small sample counts are shown explicitly and are not a statistically robust p95 estimate.

One bot-owned PR comment reports assistant-response p95 and separate task-response/greeting barge-in p95s, sample counts, and the approved SHA. CI does not upload report, audio, trace or log artifacts. Actions logs include bounded `[voice-benchmark]` lifecycle records and the complete captured stdout and stderr of failed Docker commands, including cleanup commands allowed to fail. Successful Docker commands and unrelated runner output remain suppressed. Docker failure output is no longer classified or truncated by the harness. Exact configured OpenAI, ElevenLabs and GitHub credential values are masked; this is not comprehensive sanitization. Failed container output may contain paths, URLs, provider responses, transcripts or other sensitive data, and is subject to the repository's Actions log access and retention settings. A per-run token frames failure output between the trusted harness and CI wrapper; the token is not passed to Docker. The wrapper disables Actions workflow-command processing around each output block. Lifecycle records still identify phase, exit code/signal, claim loss, cancellation/deadline and cleanup failures. Its reporter exports only validated numeric metrics; an incomplete, invalid or failed run leaves N/A values and a failing job. A started request is persisted before paid execution so queued paths cannot duplicate it after cancellation or a crash. Removing or adding either `deploy-preview` or `bench-voice` triggers benchmark reconciliation. Removing either label stops the active benchmark without starting paid work; reapplying it creates a fresh request once both labels and the approved/deployed head match. Rapid remove/re-add toggles still invalidate the old request even if both labels are present at the next check. Failed or abandoned claims are never automatically retried without a new label request. The replacement waits in the shared lifecycle queue until the previous run and its owned process/container cleanup finish, so benchmark cancellation cannot cancel deployment or teardown. Revocation is checked every 30 seconds, not instantaneously. A confirmed ownership change stops the run at that check; transient GitHub read failures are tolerated until three consecutive checks fail, and a successful read resets that counter. The old Actions job ends failed rather than with GitHub's cancelled status. A new head also revokes the run. Cancellation cannot retract a key already provided to a page.

### Barge-in latency

Full-scenario mode also runs two separately reported OpenAI Realtime interruption scenarios, once per repetition. Both interruption scenarios select and assert OpenAI Realtime through the public selector before key entry/connection; they never switch a connected session. Before connecting, both lanes prepare a private temporary PCM16 `open-calendar.wav` with the prefix before the first validated source VAD segment removed. Source and VAD sample rate/channel count must match; the cut uses source frames and preserves every remaining PCM byte. VAD at threshold 0.9 with zero padding does not prove the removed prefix was silence: a quiet initial phoneme may be clipped. In both lanes, the original `fixture.wav`, `fixtureSha256` and `fixtureVad` remain source evidence; `playback-fixture.wav` and `onsetEvidence.playbackFixture` identify the played suffix, its hash, removed frames/milliseconds and played duration/frame count. The temporary file is removed after the attempt. The task-response scenario waits for the fixed greeting to settle, plays the unchanged `only-tasks.wav` primer once, then targets only a newly identified response after that marker. A task-response earlier-gate experiment (previously 300ms) requires 100ms of that response's captured activity, marks playback and rechecks the same response with at most a 30ms quiet tail immediately before launching the prepared interruption stimulus once with zero lead-in. The report retains this `inputGate` evidence and the gate-to-captured-onset delay; a provider pause or completion at actual human onset still invalidates the attempt. The complementary greeting scenario sends no primer. Its earlier-gate experiment injects the prepared stimulus once with zero lead-in after detecting at least 100ms of accumulated active greeting audio and a 0–30ms quiet tail, rather than the previous 300ms activity gate. Negative or nonfinite observations cannot trigger playback. These experiments change stimulus scheduling, not measurement validity: the actual captured human onset must still overlap the targeted assistant audio, captured onset/window are never shifted by the trim, cancellation-evidence requirements are unchanged, and invalid or ambiguous attempts still fail. Earlier scheduling and prefix removal may avoid pauses at onset, but acoustic success remains unverified until a live run; do not compare changed stimuli/schedules as identical benchmark conditions. Both gates follow actual audio rather than assuming a fixed session offset is audible. Single-turn diagnostic mode skips both scenarios to retain exactly one playback.

`voice-barge-in-benchmark.json` and per-attempt input/output WAVs report captured human VAD onset → the beginning of confirmed assistant-output silence, on the same sample clock. Barge-in report schema version 2 uses a **controlled injected reference**, not the app-processed microphone used by older reports. Only Linux/PulseAudio barge-in scenarios opt into a second acquisition on the exact app-selected device with observed AEC, noise suppression, and AGC all disabled. Original track settings and enabled state must remain unchanged across acquisition; unverifiable settings, a mismatch, or a reference-acquisition timeout invalidate capture. Reference acquisition is bounded to two seconds; late reference tracks are retired without stopping the app track. The app receives its original stream and is never constrained, muted, replaced, or stopped by reference capture. Separate-track settings equality does not prove unchanged device acoustics, and reference buffering remains part of the measurement. Do not silently compare these latencies to earlier app-microphone results; ordinary/single-turn capture stays unchanged. Silence requires 300ms below amplitude 0.01; short pauses do not count. The stop must begin within 2 seconds, and a further 500ms guard rejects resumed interrupted output. Resumed audio is ambiguous, rather than a failure, when new or unidentified response evidence prevents attribution. Lifecycle receipt timestamps never act as exact PCM boundaries. This measures browser-rendered PCM, not physical speaker or room latency.

A matching OpenAI output-buffer clear or cancelled response corroborates an interruption. Silence without that evidence remains ambiguous: natural completion cannot be ruled out. Event timestamps are receipt-time diagnostics, not the latency endpoints. Missing capture blocks, dropped diagnostics, missing speech, and absent overlap invalidate attempts. Median/p95 include only measured stops; invalid and ambiguous counts remain visible, and the failure rate denominator is measured + failed + timeout attempts. Every requested interruption attempt must yield a measured latency for the benchmark test to pass. Invalid, ambiguous, timeout, failed, or missing attempts make the row red **after** diagnostic artifacts are attached. The root `status` and `validation` fields explain the result, and summary failures count non-measured attempts. The existing fixed-scenario response-latency report stays separate. No result claims LiveKit coverage or establishes interruption causality from audio alone.

`voice-greeting-barge-in-benchmark.json` reports the complementary greeting scenario separately. It explicitly selects **OpenAI Realtime** using the public provider selector before key entry/connection; it does not measure GPT-Live's generated opening. The fixed greeting is local Web Audio, not a remote response, so it has no OpenAI response ID. A test-only sidebranch is prepared in the one-sample unlock context and connected to the shared recorder before recording starts. The later greeting source connects only to that existing source-context tap, without changing its native speaker route, rewiring the recording graph, or rendering it twice. Source classification is demo-specific: the context must perform the inspected one-sample silent unlock, and exactly one long, direct-to-destination buffer source may occur through the snapshot. Capture must be armed before playback; unsupported shape, multiple candidates/contexts, or unavailable capture invalidate the attempt. An observed native stop at least 50ms before the source-clock expected speech end (the decoded buffer's last sample at amplitude 0.01, excluding trailing silence) corroborates truncation; natural completion stays ambiguous. The cross-context MediaStream tap adds buffering: latency measures captured tap cessation, not exact native-speaker cessation.

Capture initialization revision 2 separates preparation from recording. Processor construction/module/warm-up stages have bounded five-second deadlines and record only a stage and sanitized error category, never raw device errors. Once both inputs are connected, a single preparation request requires 100ms of continuous render frames with stable supported channel counts and present inputs; this is an engineering startup policy, not a browser guarantee or a speech-amplitude condition. One five-second wall-clock preparation deadline is never restarted by instability. Readiness, markers, and sample-clock access require the processor's recording acknowledgment. Remote output passes through during preparation without microphone feedback; early output may be outside the recorded window. The first recorded frame is explicit, and no post-start gap is ever reset, coalesced, or discarded. A late recording acknowledgment cannot revive timed-out readiness, but its actual boundary and subsequent integrity evidence remain available in diagnostics. Raw storage retains the existing ten-minute cap; any later integrity-detail omissions are counted explicitly. Results from earlier initialization revisions do not validate this revised setup.

Each attempt retains `captureIntegrity` with setup/preparation diagnostics (duration, resets, deadline, first captured frame), block count, missing-block count, and detailed frame-gap/format/absent-channel reasons. Missing blocks still invalidate production measurements; waveform zeros alone cannot distinguish recorded silence from filled capture gaps.

Both barge-in reports retain `onsetEvidence`: the generated fixture SHA-256, fixture VAD preflight, captured VAD segments, playback sample bounds, and the selected onset even when overlap validation rejects it. Each attempt archives its source as `*-fixture.wav` before temporary-fixture cleanup. VAD threshold/padding are unchanged; onset is never backdated from fixture playback or rewritten to rescue a result.

Greeting input/output WAVs contain the aligned controlled reference and greeting target only. A separate `greeting-barge-in-<n>-speaker-monitor.wav` retains native greeting and later remote replies. Follow-up capture waits for a changed assistant caption, listening state, and one second of speaker quiet, bounded by 30 seconds; `followupCapture: timeout` means the later response may be incomplete. This diagnostic neither changes greeting latency nor proves task success.


By default, tests target the local app at `http://localhost:3000` (or the documented `MAELSTROM_HOST` forwarding host). For the documented local server-key workflow, set `OPENAI_API_KEY` in the ignored root `.env`, leave `DEMO_LOCAL_SERVER_KEY=0`, and start from the workspace root with `VITE_VOICE_PROVIDER=realtime bunx nx dev demo`. This explicitly selects OpenAI Realtime instead of the fresh-visit GPT-Live default. Ordinary suites use the app's initial provider; both interruption benchmarks explicitly select Realtime before connection. Unset or empty `MAELSTROM_BASE_URL` selects this local mode, preserving `MAELSTROM_APP_PORT`/`MAELSTROM_WS_PORT` forwarding and local readiness checks. To target a hosted deployment instead, set `MAELSTROM_BASE_URL` to its HTTP or HTTPS URL, for example `MAELSTROM_BASE_URL=https://demo.maelstrom-ai.co/ bunx nx run @maelstrom-co/demo:voice-e2e`. Remote mode checks that URL and uses it as Playwright's browser base URL; it does not inspect or forward local app ports. No `MAELSTROM_E2E_OPENAI_API_KEY` is needed for this local Realtime server-key mode; the app still needs its server-held `OPENAI_API_KEY`. If ports 3000/3001 belong to another checkout, run this checkout's servers separately, without stopping that checkout:

```sh
WS_PORT=3011 bun --cwd apps/demo run dev:ws
VITE_VOICE_PROVIDER=realtime VITE_WS_URL=ws://localhost:3001 bunx nx run @maelstrom-co/demo:serve --host=0.0.0.0 --port=3010
MAELSTROM_APP_PORT=3010 MAELSTROM_WS_PORT=3011 bunx nx run @maelstrom-co/demo:voice-e2e
```

The container forwards those host ports to Chromium on localhost:3000/3001:

```text
Chromium (container)       Host (this checkout)
localhost:3000         ->  localhost:3010 (Vite)
localhost:3001         ->  localhost:3011 (Engine WebSocket)
```

`VITE_WS_URL=ws://localhost:3001` above is intentionally the container browser's
address, not the host listener. Do not change it to `3011` for this runner: the
container listens on `3001`. To browse this alternate-port app directly on the
host instead, use `VITE_WS_URL=ws://localhost:3011` and restart Vite; that separate
configuration is not the container test setup.

This local Realtime server-key mode does not require an E2E key. Authenticated local GPT-Live is not this workflow: its Vite listener is loopback-only and HTTP-authenticated, while these suites do not configure HTTP credentials. Do not disable its access checks to make container forwarding work. Use an explicitly configured BYOK target for Live, or add a separately verified authenticated host integration. Each test creates its own browser context and page, navigates to the configured target URL (including path and query), and verifies the public seed contains `calendar-main` and `tasks-main` plus the voice controls. The clean page creates a fresh workspace/voice/conversation session without a product reset action or test-only endpoint. Hosted deployment seed/configuration is not verified by this local setup.

For a hosted or other BYOK deployment, export `MAELSTROM_E2E_OPENAI_API_KEY` in the shell that runs the Nx target. The worker reads the value once into process memory; each isolated test page re-enters it through the actual password-masked drawer UI using DOM setter/input events (never a secret-valued Playwright fill action), scoped to the popup's `Add key` or `Save` button. If the app requires BYOK and the variable is absent, setup fails with an actionable message. Never place the key in repository files, fixture text, command-line arguments, logs, reports, traces, or artifacts. Hosted browser execution and the currently deployed target's configuration remain unverified.

Fixture preparation is separate from the app's voice provider. The supported credentialed setup in this runner is `TTS_PROVIDER=elevenlabs` (also the default), with `ELEVENLABS_API_KEY` and optional `ELEVENLABS_VOICE_ID`. `ELEVENLABS_OUTPUT_FORMAT` defaults to `pcm_16000`. These are used only to regenerate deterministic-named speech fixtures; matching cached audio may avoid synthesis. The runner passes other `TTS_PROVIDER` values through to the image but forwards only ElevenLabs key/voice credentials. Other TTS providers are not a documented supported preparation path; changing that variable alone does not configure their credentials. TTS responses are cached on the host and reused across fixture-generation runs. By default the cache is `$XDG_CACHE_HOME/tts2mic-mcp` when `XDG_CACHE_HOME` is set, otherwise `$HOME/.cache/tts2mic-mcp`. Set `MAELSTROM_TTS_CACHE_DIR` to an alternate host directory; relative overrides resolve from the current working directory. The resolved directory must be writable and outside the repository; an in-repository path is rejected, including when reached through a symlink. The directory is created if needed. To clear the default cache, remove that directory (or remove the configured override directory) when no test run is using it. Cache identity includes provider, language, voice, text hash, and output format where supported, but ElevenLabs cache identity does not include model ID; switching models may therefore reuse audio cached for another model. Generated speech persists outside the repository and may be sensitive; protect the cache accordingly and clear it when no longer needed.

Each ordinary conversation report attaches exactly two full-session WAVs: captured human microphone input and assistant-rendered output, with matching sample rate and frame timeline. Capture limitations are recorded explicitly instead of attaching synthetic or mismatched WAVs. Reports also retain protocol projection and recorder diagnostics. Playwright traces, screenshots, and video are disabled because browser artifacts may capture credential-sensitive pages. Protocol evidence projects only chart layout identifiers and excludes credentials, transcript/intention text, vessel definitions, and auth payloads.
