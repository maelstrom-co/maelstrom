# Demo voice end-to-end tests

## Reusing browser mechanics

Voice suites use the local driver for navigation, observations, browser evaluation/snapshots, shared-audio hooks, protocol evidence, and bounded subprocess cleanup while keeping scenario setup and benchmark policy in the suite:

```ts
import { test } from './voice-test-fixture.ts';

test('voice scenario', async ({ page, voiceDriver }) => {
  await voiceDriver.navigate(process.env.MAELSTROM_BASE_URL);
  const before = voiceDriver.cursor();
  // Scenario-specific key setup and actions stay in the consumer.
  await page.getByRole('button', { name: 'Start voice' }).click();
  await voiceDriver.waitForObservation(
    (event) => event.type === 'voice-state',
    { after: before, timeoutMs: 10_000, signal: voiceDriver.signal },
  );
  const snapshot = await voiceDriver.snapshot();
  voiceDriver.assertHealthy('scenario setup');
});
```

Observations identify the run/page, carry monotonically increasing sequence numbers, and retain separate Node-monotonic and browser-performance clock domains. The bounded buffer exposes overflow and rejects expired cursors rather than silently skipping events. The Playwright fixture records evidence and disposes its browser instrumentation automatically; `navigate(baseURL, false)` skips AudioWorklet capture when unnecessary. Use `startVoiceProcess` for playback commands that must be cancelled with the driver lifecycle; termination escalates from SIGTERM to SIGKILL.

Run the standalone benchmark on Linux with `TTS2MIC_BIN` and `PULSE_SERVER` set (normally supplied by the voice-devtools container), using its separate Playwright configuration and no test retries:

```sh
bunx playwright test --config apps/demo/e2e/voice/playwright.benchmark.config.ts
```

The app must already be running; prepare the fixed WAV fixtures as for the voice E2E suite. Set `VOICE_BENCHMARK_REPETITIONS` to an integer from 1 to 3 (default `1`) to repeat the fixed scenarios explicitly. Recorder and test time limits scale to the requested repetitions. The JSON and exactly two complete session WAVs are attached to the Playwright run. Ordinary conversation tests likewise attach exactly two complete session WAVs: the actual captured microphone input and assistant-rendered output, aligned to the same 48 kHz frame timeline. Captured active-audio duration is threshold-based non-silence, not VAD-ground-truth speech duration. Turn boundaries use the voice UI returning to connected/listening plus one second of quiet monitor audio; pauses may still make a boundary ambiguous. Latency is reported per human VAD segment using two complete session WAV attachments on one 48 kHz browser AudioContext/AudioWorklet clock: the human track is the actual injected `getUserMedia` microphone track used by the app, and the assistant track is the actual WebRTC `MediaStream` assigned to the app `HTMLAudioElement`, routed through the shared graph and rendered exactly once before the physical speaker sink. Both WAVs have the same frame range and sample rate; latency sample offsets address these files. Assistant latency is browser-rendered, not physical-speaker loopback. Voice-devtools VAD runs on the captured input WAV with threshold `0.9` and zero boundary padding; t=0 is the first VAD sample. Human VAD segments separated by no more than 500 ms are grouped as one turn. Assistant onset uses a `0.01` sample threshold and merges sub-10 ms quiet gaps. Overlap, unanswered turns, missing blocks, and unaligned frames are unsupported. The PulseAudio monitor remains a separate active-audio measure. UI state and monitor silence orchestrate scenario completion only, not latency. Barge-in overlap, reliable transcript word count, and WPM remain unsupported.

From the workspace root, run `bunx nx run @maelstrom-co/demo:voice-e2e`. Its TypeScript runner prepares three speech fixtures, launches the serial Chromium voice scenarios in the voice-devtools container, collects the HTML report and diagnostics under `apps/demo/dist/docker-voice`, and opens `report/index.html` on macOS. The Nx target is uncached and non-parallel. Docker orchestration uses the installed Docker CLI through Node's `child_process` API, so no Docker SDK dependency is required; the runner preserves a failing test exit status after collecting and opening the report.

Run the dedicated containerized benchmark from the workspace root with `bunx nx run @maelstrom-co/demo:voice-benchmark`. It uses the same voice-devtools image and fixture preparation but selects `playwright.benchmark.config.ts`, including its deterministic shared-AudioWorklet capture test; it does not change the ordinary voice E2E suite. The benchmark verifies that the image exposes `tts2mic-mcp vad` before running VAD. The host collects Playwright's HTML report, benchmark JSON/WAV attachments, runner metadata, and Docker log under `apps/demo/dist/docker-voice/` (`report/index.html` and `benchmark-results/`). Prerequisites are Docker, a running reachable demo app, and the voice-devtools audio container's Linux/PulseAudio/TTS2MIC setup. The host prepares the three scenario WAV fixtures before launch; preparing the generated fixtures needs the configured TTS provider's credentials unless matching audio is already cached (for ElevenLabs, `ELEVENLABS_API_KEY` and optionally `ELEVENLABS_VOICE_ID`). Local mode defaults to `http://localhost:3000` and the configured WebSocket port; `MAELSTROM_HOST`, `MAELSTROM_APP_PORT`, and `MAELSTROM_WS_PORT` can configure host forwarding. For a BYOK target, provide `MAELSTROM_E2E_OPENAI_API_KEY` in the host shell; it is passed only into the benchmark container when present and is never printed by the runner. Set `VOICE_BENCHMARK_REPETITIONS` to 1–3 (default 1). Do not pass provider secrets such as `DEEPGRAM_API_KEY` to the audio container. Full-scenario benchmark retry count remains zero. Set `VOICE_BENCHMARK_SINGLE_TURN=1` in the host shell to opt into exactly one playback of the full `only-tasks.wav` human fixture and wait for that assistant response; this mode always reports one repetition and the selected scenario. Its fixture VAD preflight and captured input retain all raw VAD segments; multiple speech islands are treated as one logical command for this known single-playback fixture. The latency window spans the first raw VAD start through the last raw VAD end, and latency is measured from that final end only when assistant output does not overlap any part of the command. Empty VAD results, overlap, or ambiguous output leave latency unsupported. It does not trim audio or synthesize turn boundaries. Each single-turn attempt records expected and captured raw-VAD active milliseconds and their ratio; a ratio below 50% invalidates the attempt. This conservative coverage check is diagnostic rather than proof that identical speech content was captured. Unsupported latency caused by assistant onset before the final human VAD end or overlap also invalidates the attempt. Invalid attempts attach their sanitized report before failing, and single-turn mode alone gets three built-in Playwright retries (four total attempts with retry indices 0–3); the report's attempt index distinguishes each attempt. Persistent invalidity remains a failed test, never a reported latency. For example: `VOICE_BENCHMARK_SINGLE_TURN=1 bunx nx run @maelstrom-co/demo:voice-benchmark`. Without this flag, all three scenarios, existing repetition behavior, and zero retry behavior remain unchanged. In full-scenario mode, each fixture must produce at least 150ms of activity on the captured assistant WebRTC track or fail after 30 seconds. Before every next fixture, the runner continuously rechecks that assistant-only track and releases input only after its existing 1-second completion-quiet interval plus a 2-second post-speech buffer, and after the prior source-audio end-to-next-source-onset gap reaches 30 seconds. A resumed assistant burst resets the quiet/buffer wait; if one is detected during the `tts2mic` 3-second lead-in, playback is stopped and the attempt fails closed because the runner exposes no proof that source audio had not begun. The fixture is never replayed after an uncertain cancellation. The lead-in is included when scheduling source onset, not added to the 30-second gap. This pacing is not applied to the one-fixture single-turn diagnostic. The benchmark's active-audio duration and turn boundary are approximate; human-first-input latency, barge-in, transcript word count, and WPM remain unsupported. A live measurement still requires a credentialed run against the configured app/provider; deterministic configuration tests do not provide live latency data.


By default, tests target the local app at `http://localhost:3000` (or the documented `MAELSTROM_HOST` forwarding host); start the local server-key demo with `bun --cwd apps/demo run dev`. Unset or empty `MAELSTROM_BASE_URL` selects this local mode, preserving `MAELSTROM_APP_PORT`/`MAELSTROM_WS_PORT` forwarding and local readiness checks. To target a hosted deployment instead, set `MAELSTROM_BASE_URL` to its HTTP(S) URL, for example `MAELSTROM_BASE_URL=https://demo.maelstrom-ai.co/ bunx nx run @maelstrom-co/demo:voice-e2e`. Remote mode checks that URL and uses it as Playwright's browser base URL; it does not inspect or forward local app ports. No API key is needed for local server-key mode. If ports 3000/3001 belong to another checkout, run this checkout's servers separately, without stopping that checkout:

```sh
WS_PORT=3011 bun --cwd apps/demo run dev:ws
VITE_WS_URL=ws://localhost:3001 bunx nx run @maelstrom-co/demo:serve --host=0.0.0.0 --port=3010
MAELSTROM_APP_PORT=3010 MAELSTROM_WS_PORT=3011 bunx nx run @maelstrom-co/demo:voice-e2e
```

The container forwards those host ports to Chromium on localhost:3000/3001. Local server-key mode does not require an E2E key. Each test creates its own browser context and page, navigates to the configured target URL (including path and query), and verifies the public seed contains `calendar-main` and `tasks-main` plus the voice controls. The clean page creates a fresh workspace/voice/conversation session without a product reset action or test-only endpoint. Hosted deployment seed/configuration is not verified by this local setup.

For a hosted or other BYOK deployment, export `MAELSTROM_E2E_OPENAI_API_KEY` in the shell that runs the Nx target. The worker reads the value once into process memory; each isolated test page re-enters it through the actual password-masked drawer UI using DOM setter/input events (never a secret-valued Playwright fill action), scoped to the popup's `Add key` or `Save` button. If the app requires BYOK and the variable is absent, setup fails with an actionable message. Never place the key in repository files, fixture text, command-line arguments, logs, reports, traces, or artifacts. Hosted browser execution and the currently deployed target's configuration remain unverified.

`TTS_PROVIDER`, `ELEVENLABS_API_KEY`, and `ELEVENLABS_VOICE_ID` are needed only to regenerate deterministic-named speech fixtures. TTS responses are cached on the host and reused across fixture-generation runs. By default the cache is `$XDG_CACHE_HOME/tts2mic-mcp` when `XDG_CACHE_HOME` is set, otherwise `$HOME/.cache/tts2mic-mcp`. Set `MAELSTROM_TTS_CACHE_DIR` to an alternate host directory; relative overrides resolve from the current working directory. The resolved directory must be writable and outside the repository; an in-repository path is rejected, including when reached through a symlink. The directory is created if needed. To clear the default cache, remove that directory (or remove the configured override directory) when no test run is using it. Cache identity includes provider, language, voice, text hash, and output format where supported, but ElevenLabs cache identity does not include model ID; switching models may therefore reuse audio cached for another model. Generated speech persists outside the repository and may be sensitive; protect the cache accordingly and clear it when no longer needed.

Each ordinary conversation report attaches exactly two full-session WAVs: captured human microphone input and assistant-rendered output, with matching sample rate and frame timeline. Capture limitations are recorded explicitly instead of attaching synthetic or mismatched WAVs. Reports also retain screenshots, protocol projection, and recorder diagnostics. Playwright traces are disabled because a trace may capture password-input events. Failure screenshots remain enabled; the key drawer uses a password input. Protocol evidence projects only chart layout identifiers and excludes credentials, transcript/intention text, vessel definitions, and auth payloads.
