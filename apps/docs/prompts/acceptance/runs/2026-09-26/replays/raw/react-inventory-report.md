## SDK API/version evidence and constraints

The checked-out `packages/react` source and installed `0.1.0-alpha.4` declarations were inspected, together with protocol definitions and SDK tests (tests were read, not run):

- React `src/index.ts` exports `createMaelstrom`, `vessel`, `defineVessel` (re-export from protocol), `ChartProps`, `MaelstromProviderProps`, and `TypedVesselProps` among other APIs. React `src/lib/create-maelstrom.ts` accepts `{ vessels: [...] }` and returns a typed instance with `Provider`, `Chart`, and hooks. `src/lib/vessel.ts` defines eager `vessel(definition, Component)` and lazy loader overloads. A Vessel Component receives `instanceId`, `variantProps`, and `executeAction`; the existing SearchPanel does not need those values, but this compatibility still needs typecheck after an approved integration.
- Protocol `src/lib/vessel.ts` defines `defineVessel` as a literal-preserving helper and the `VesselDefinition` shape: `id`, `name`, `description`, `defaultVariant`, and at least one variant. Each variant requires `props`, `minSize`, and `actions`; validation requires a declared default Variant. `actions: []` is supported. There is no evidenced SearchPanel operation appropriate for an Engine-executed Action; the form submit remains an end-user form event and calls the application-owned search function.
- React `src/lib/provider.tsx` requires a real `EngineConnector` prop and constructs/connects an Orchestrator on mount; `initialLayout` is an optional proposed first screen only in tiling mode and can be changed by the Engine response. React `src/lib/chart/chart.tsx` renders Vessel instances according to Chart layout, with `ChartProps` children as an independent slot. This API makes Connector and initial placement/product behavior important integration seams, not details that can be inferred here.
- SDK source tests inspected include `packages/react/src/lib/create-maelstrom.test.ts` (literal IDs/static vessel entries) and `packages/react/src/lib/register-vessel.test.tsx` (dynamic registration). These establish source-supported library APIs, not evidence of successful app integration or live Engine behavior. Installed declaration files inspected include `node_modules/@maelstrom-co/react/dist/lib/{vessel,create-maelstrom,provider,vessel-entry-types}.d.ts` and `node_modules/@maelstrom-co/protocol/dist/lib/vessel.d.ts`.

## Bounded implementation and verification plan (proposed only)

**Blocking product/architecture decision before editing:** determine how Engine-selected placement can coexist with the current app behavior. Today SearchPanel always renders directly in `<main>`. A Chart-owned placement may move, omit, or duplicate it; keeping both an always-visible form and a placeable instance may create two independently stateful forms. No app connector or auth owner is evidenced. The repository owner must choose the Connector source/auth ownership and whether the form is moved into Chart, remains as a static UI plus a separate vessel, or has some other expressly approved presentation. Do not choose for them, use `src/testConnector.ts` in production, or invent geometry/layout reconciliation.

Conditional, minimal sequence after that decision:

1. Define a developer-authored Vessel with a single default search Variant, empty app props if none are needed, and `actions: []`; wrap/register the existing `SearchPanel` using the exact `defineVessel`/`vessel` API available in installed v`0.1.0-alpha.4`. Choose the required `minSize` only after the approved Chart sizing/layout decision; no numeric size is evidenced by current UI.
2. At only the approved application seam (`src/App.tsx` and, if the selected composition requires it, `src/main.tsx`), construct the Maelstrom instance from the static Vessel entry and use the owner-approved Connector with `Provider`/`Chart`. Preserve the heading, copy, controlled input, submit behavior, helper boundary, and feedback semantics. Keep `searchTickets` and any future real API/auth decisions application/server-owned; do not put secrets in browser code. Do not add routes, persistence, retries, model-generated JSX, or new operations.
3. Focused tests/checks after an implementation is authorized: extend the existing `src/SearchPanel.test.tsx` assertions for controlled input, empty/whitespace-disabled submit, pending state, success count and generic error; add a focused registration/render test with a mock/simulated Connector response that explicitly includes a layout placement for the static Vessel. Any such stub proves only local API/render behavior. Run the declared `npm run typecheck`, `npm test`, and `npm run build` after changes. Verify live Engine separately only with approved service/credentials; the existing test Connector is not a live Engine check.

Rollback: remove only the new Vessel definition/entry, factory Provider/Chart wiring, and integration wrapper from the approved seam; restore `App` to the current heading/text/direct `<SearchPanel />` composition and leave `SearchPanel.tsx`/`search.ts` behavior intact. No rollback was needed because no edits were made.
