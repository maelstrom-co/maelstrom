import { Steps, Aside } from '@astrojs/starlight/components';

API reference pages on this site are generated from each package's `src/index.ts`
exports and their JSDoc — no markdown is hand-written between a code change and
a docs rebuild. Anything you re-export from a package barrel becomes a public
page; anything you don't, doesn't.

## Before you start

- The symbol you want to document must be re-exported from the package's
  `src/index.ts`. Helpers reachable only inside the package aren't in the
  public API and don't appear in Reference.
- The package's `tsconfig.lib.json` must already include the file the symbol
  lives in. Every published package does; new files inside an existing
  package are picked up automatically.

## Steps

<Steps>
1.  **Write a JSDoc block above the export.** Lead with what the symbol does
    and any load-bearing invariant; skip what the type already shows.

    ```ts title="packages/engine/src/lib/engine.ts"
    /**
     * Construct an Engine from the given config.
     *
     * Validates `config` synchronously and **throws** on invalid input.
     * Invalid config is a programmer error, not a runtime condition.
     */
    export function createEngine(config: EngineConfig): Engine {
      // ...
    }
    ```

2.  **Cross-reference other symbols with `{@link Name}`.** Bare names render as
    plain text; `{@link}` resolves to an intra-site link, including member
    references like `{@link Engine.handle}`.

    ```ts
    /**
     * Routes on `message.type`. See {@link createEngine} for construction
     * and {@link EngineError} for the failure channel.
     */
    handle(message: EngineMessage): Promise<Result<EngineOutput, EngineError>>;
    ```

3.  **Mark barrel-exported helpers that aren't user-facing with `@internal`.**
    If a symbol is re-exported from `src/index.ts` only because a sibling
    `@maelstrom-co` package needs to import it, tag it `@internal`. The
    generator is configured with `excludeInternal: true`, so the symbol
    stays reachable to TypeScript but does not appear in the docs site.
    Symbols that aren't re-exported from the barrel are already invisible
    to the generator — `@internal` is unnecessary there.

    ```ts
    /**
     * Wire helper for cross-package consumers.
     *
     * @internal
     */
    export function someBarrelExportedHelper(): SomeShape {
      // ...
    }
    ```
</Steps>

## Variations

### Add a runnable example

Use `@example` followed by a fenced code block. The plugin renders it as an
`## Example` section under the symbol.

```ts
/**
 * Build the system + user prompt halves.
 *
 * @example
 * ```ts
 * const { systemPrompt, userPrompt } = buildPrompt(request, {
 *   vars: { assistantName: 'Aria' },
 * });
 * ```
 */
export function buildPrompt(request: ChartRequest, options?: PromptOptions): PromptResult;
```

### Deprecate a symbol

`@deprecated` renders inline with a strikethrough badge; pair it with a pointer
to the replacement.

```ts
/**
 * @deprecated Use the disposer returned by {@link registerRunner} instead.
 */
unregisterRunner(instanceId: InstanceId): void;
```

### Document throw conditions

`@throws` renders as its own section. Keep the body in prose — the leading
`{TypeName}` is parsed by TypeDoc and stripped from the rendered text.

```ts
/**
 * @throws If `config` fails Zod validation, or if a system-prompt
 *   customizer is misconfigured.
 */
export function createEngine(config: EngineConfig): Engine;
```

## What not to do

- **Don't restate the type signature in prose.** The reference page already
  shows it. If hovering the symbol gives the reader the same information,
  the prose is filler.
- **Don't put `TODO(...)` notes inside JSDoc blocks.** They render verbatim
  on the public page. Use regular `//` comments next to the implementation
  instead.
- **Don't use `##` or deeper Markdown headings inside JSDoc.** TypeDoc emits
  its own `##` sections (`Parameters`, `Returns`, `Throws`, `Example`).
  Authoring sibling `##` headings inside a comment block produces a jumbled
  page hierarchy. Stick to prose paragraphs and bullet lists.
- **Don't document a non-exported symbol expecting it to appear.** Only
  symbols re-exported from `src/index.ts` are reachable to the generator.

<Aside type="note">
  Cross-package `{@link}` resolution (e.g. an `engine` JSDoc linking to a
  `protocol` type) is not wired up. Those references render as plain text
  on the docs site, even though TypeScript resolves them correctly at
  authoring time.
</Aside>

## Verify

Build the docs and open the generated page for the symbol you changed:

```bash
nx build docs
```

Find the page under `apps/docs/dist/reference/<package>/<kind>/<symbol>/index.html`
and confirm the prose, parameters, returns, and any `{@link}` cross-references
render as expected. For an iterative loop, `nx dev docs` regenerates on
startup — restart the dev server after editing JSDoc to see the change.
