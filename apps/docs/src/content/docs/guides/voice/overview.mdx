Voice gives users another way to express intent. It does not give a speech provider control of the Chart: both shipped voice tracks submit a natural-language intent through `RealtimeSession`, and the Engine still plans from the client-built Chart snapshot.

<Aside type="caution" title="Keep credentials on the server">
  Never send provider API keys or LiveKit secrets to the browser. Token minters
  are unauthenticated bootstrap primitives; put caller authentication and
  authorization, trusted session policy, origin or room controls, rate limits,
  and abuse monitoring in front of them before production use.
</Aside>

## Choose a voice track

Maelstrom ships two tracks behind the same session boundary:

| Track | Interaction | Provider path | Grounding |
| --- | --- | --- | --- |
| OpenAI Realtime | Speech-native conversation with provider-managed turn detection | Browser-direct WebRTC using a short-lived credential minted by your server | The realtime model receives debounced structural summaries and can pull current UI state |
| LiveKit cascade | Hold-to-talk | LiveKit carries audio to a worker for Deepgram speech-to-text and Cartesia text-to-speech | The worker has no LLM and receives no grounding |

[Choose OpenAI Realtime](/guides/voice/openai-realtime/) when you want a speech-native model to manage the conversation. [Choose the LiveKit cascade](/guides/voice/livekit-cascade/) when you want explicit hold-to-talk turns and a worker that performs only speech recognition and synthesis.

## Follow the shared intent boundary

The voice path rejoins the normal Maelstrom request loop before planning:

1. A provider adapter produces a natural-language intent.
2. `RealtimeSession` submits that intent through the client.
3. The client captures the current Instances, Variants, and Chart dimensions.
4. The Engine returns an Execution Plan and a Layout Directive for each affected Instance.
5. The client applies the result and reports that rendering has settled.

The provider never supplies Vessel IDs, Actions, or layout coordinates as planning input. Read the [Architecture Overview](/understanding/architecture/) for the request and render loop that voice reuses.

## Know the package boundaries

The voice packages separate browser, server, and worker responsibilities:

| Package | Runtime | Responsibility |
| --- | --- | --- |
| [`@maelstrom-co/realtime`](/reference/realtime/readme/) | Browser | Provider-neutral session, intent routing, speak-after-render ordering, and structural grounding |
| [`@maelstrom-co/realtime/openai`](/reference/realtime/packages/realtime/src/openai/classes/openaiadapter/) | Browser | OpenAI WebRTC transport and token grant schemas |
| [`@maelstrom-co/react-realtime`](/reference/react-realtime/readme/) | Browser | Shared React session, `useVoice()`, transcripts, state, and `VoiceOrb` |
| [`@maelstrom-co/realtime-server`](/reference/realtime-server/readme/) | Server | Exchange a server-held OpenAI API key for a short-lived client credential |
| [`@maelstrom-co/realtime-livekit`](/reference/realtime-livekit/readme/) | Browser | LiveKit room transport, final-transcript intent conversion, and hold-to-talk control |
| [`@maelstrom-co/realtime-livekit-server`](/reference/realtime-livekit-server/readme/) | Server | Sign a short-lived grant for one LiveKit room and participant identity |
| [`@maelstrom-co/realtime-livekit-agent`](/reference/realtime-livekit-agent/readme/) | Worker | Run Deepgram STT and Cartesia TTS without an LLM or UI grounding |

These boundaries keep `OPENAI_API_KEY`, LiveKit secrets, and speech-provider keys out of browser code. They also keep provider transport details out of the Engine.
