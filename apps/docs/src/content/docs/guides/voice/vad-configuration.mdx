This guide is for browser-side VAD tuning in a Maelstrom app that already has voice wired up. Use it when pickup feels late, endings get clipped, the mic triggers too easily, or barge-in gets messy during playback.

Keep the scope tight. `vadOptions` tune browser speech detection. Backend timing and voice system architecture live elsewhere. If you need the full split, read [Voice Architecture](/understanding/voice-architecture/). If you need backend runtime timing controls, read [`createVoiceSession()`](/reference/voice-server/functions/createvoicesession/). If you only need the field contract, read [`VADConfig`](/reference/voice/interfaces/vadconfig/).

## Start by naming the layer

Maelstrom has two different timing layers, and they solve different problems.

- **Browser VAD**, configured with `vadOptions`, decides when local speech starts, when it ends, how much leading audio to keep, and how long one user turn may run.
- **Backend runtime timing**, configured with fields such as `vadFinalDebounceMs` and `transcriptGraceMs`, decides how the backend treats a turn after the browser already marked it complete.

Don't mix them. If the problem is pickup, clipping, fragmentation, or playback false triggers, start with browser `vadOptions`. If the browser already detects turns well and the backend still feels cautious, look at the backend runtime docs instead.

## Browser VAD fields at a glance

| Field | Default | What it changes |
| --- | --- | --- |
| `minSpeechDurationSeconds` | `0.05` | How much continuous speech the browser needs before it emits `speech_start`. |
| `minSilenceDurationSeconds` | `0.8` | How much continuous silence the browser needs before it emits `speech_end`. |
| `activationThreshold` | `0.7` in low-level `@maelstrom-co/voice`, `0.5` effective default through `m.useVoice()` | How confident the browser must be before a chunk counts as speech. |
| `preSpeechPaddingSeconds` | `0.3` | How much recent audio to prepend when speech starts. |
| `maxUserTalkingDurationSeconds` | session fallback of `60` seconds when omitted | Upper cap for one continuous user turn when silence never settles. |

That table is the map. The tuning work is deciding which symptom points to which field.

## Field-by-field tuning guidance

### `minSpeechDurationSeconds`

Default: `0.05`

Lower it when the browser is slow to react to short commands like "stop" or "wait". Raise it when taps, bumps, or room noise keep creating false starts.

Tradeoff:

- Lower values feel snappier, but they trust tiny bursts more easily.
- Higher values feel steadier, but they delay pickup and can weaken barge-in.

### `minSilenceDurationSeconds`

Default: `0.8`

Lower it when the app waits too long before handing the turn to STT and the engine. Raise it when normal pauses keep splitting one thought into multiple turns.

Tradeoff:

- Lower values feel faster, but they can cut off trailing words.
- Higher values sound more natural, but they add latency.

Change this late in the process. It has the biggest effect on how fast or fragmented the whole loop feels.

### `activationThreshold`

Default: `0.7` in low-level `@maelstrom-co/voice`. If you use `m.useVoice()`, `@maelstrom-co/react-voice` currently merges your overrides on top of `activationThreshold: 0.5`.

Raise it when background noise, keyboard sounds, or playback leakage keep looking like speech. Lower it when users speak softly or the mic gain is weak.

Tradeoff:

- Higher values reject more noise, but they can miss quiet voices.
- Lower values catch soft speech, but they trigger more easily.

### `preSpeechPaddingSeconds`

Default: `0.3`

Raise it when the first syllable keeps getting chopped off. Lower it when you want a tighter leading edge and don't need as much pre-roll.

Tradeoff:

- More padding protects speech starts.
- Less padding keeps the capture tighter.

### `maxUserTalkingDurationSeconds`

Default: session fallback of `60` seconds when omitted

Lower it when your product expects short command turns. Raise it when people dictate longer thoughts and you would rather tolerate a very long turn than force an early boundary.

Tradeoff:

- Lower values keep sessions moving.
- Higher values avoid forced segmentation on long speech.

Treat this as a safety rail, not your main tuning knob.

## Demo calibration example

The demo only overrides two values:

```ts
vadOptions: {
  minSpeechDurationSeconds: 0.032,
  preSpeechPaddingSeconds: 0.45,
}
```

That is a good pattern to copy.

- `minSpeechDurationSeconds: 0.032` makes short utterances and barge-in feel more immediate.
- `preSpeechPaddingSeconds: 0.45` keeps more leading audio so the faster trigger does not clip the start.

Start from the defaults, then change one or two values for a clear reason. If you still need the full integration setup, go back to [Voice Integration](/guides/voice/voice-integration/).

## Playback and AEC caveat

While assistant TTS is playing, the browser VAD raises its live speech threshold to `0.8`.

- Low-level browser runtime path: `0.7` to `0.8`
- `m.useVoice()` path: `0.5` to `0.8`

That helps when browser AEC is doing its job, because assistant playback is more likely to stay out of the mic path. It is still a mitigation, not a guarantee. If playback audio keeps retriggering the mic, use the fallback actions below instead of chasing one magic threshold.

## Degraded browser or VAD fallback actions

Use the symptom first, then make the smallest possible change.

### Symptom: assistant playback retriggers the mic

1. Raise `activationThreshold` a little.
2. If the false trigger mostly happens during playback, set `allowBargeIn: false` so user audio is ignored while the assistant is speaking.
3. If the device or browser still leaks playback badly, switch that flow to manual start or keep typed input visible as the primary fallback.

Use this path for weak AEC, speakerphone-like setups, or kiosk hardware that feeds playback back into the mic.

### Symptom: the mic triggers on room noise or keyboard sounds

1. Raise `activationThreshold`.
2. If noise still causes short false starts, raise `minSpeechDurationSeconds` a little.
3. If users then need to shout to get pickup, back off the threshold and fix the environment first, headset, mic placement, or room noise, before stacking more VAD changes.

### Symptom: speech starts late or the first syllable is clipped

1. Raise `preSpeechPaddingSeconds`.
2. If pickup still feels late on short commands, lower `minSpeechDurationSeconds` slightly.
3. Stop once the start sounds natural. If you lower both too far, noise starts will come back.

### Symptom: one sentence gets split into several turns

1. Raise `minSilenceDurationSeconds`.
2. If the app then feels too slow to respond, back it down and test with real pauses, not just continuous reading.
3. If the same browser still fragments turns in noisy rooms, keep the milder value and offer typed input for longer or more complex requests.

### Symptom: turns take too long to finish

1. Lower `minSilenceDurationSeconds`.
2. If that clips word endings, restore part of the change and accept the slightly slower handoff.
3. Only after the browser end feels right should you look at backend timing like `vadFinalDebounceMs` or `transcriptGraceMs`.

### Symptom: voice works on one device, but another browser cannot start VAD cleanly

1. Surface the failure in your UI through `onError` so the session does not silently fail.
2. If `useVoice()` reports missing or broken browser voice support, hide or disable the voice button or auto-start path for that device.
3. Keep a typed or non-voice path available and point users to it immediately instead of asking them to retry the same broken voice flow.

This is the fallback path for missing browser support, broken dependency loading, or model/Wasm startup failures. Voice should degrade to another control path, not to a dead button.

## Practical tuning workflow

Stay on browser `vadOptions` while the problem is pickup, clipping, fragmentation, or playback retriggers. If local turns already feel right and only the backend handoff still feels slow or cautious, stop tuning here and move to [`createVoiceSession()`](/reference/voice-server/functions/createvoicesession/). For the full layer split, read [Voice Architecture](/understanding/voice-architecture/).

If you are tuning from scratch, use this order:

1. Keep the defaults.
2. Test in one quiet room and one noisy room.
3. Fix clipped starts with `preSpeechPaddingSeconds` before changing multiple thresholds.
4. Fix late pickup with `minSpeechDurationSeconds`.
5. Fix false triggers with `activationThreshold`.
6. Fix fragmented or sluggish endings with `minSilenceDurationSeconds` last.
7. Change one field at a time and keep notes on what improved and what got worse.
8. If the browser environment stays unreliable, stop tuning and move that path to manual start or typed input.

That last step matters. A bad browser or audio setup is not always fixable with more threshold changes.
