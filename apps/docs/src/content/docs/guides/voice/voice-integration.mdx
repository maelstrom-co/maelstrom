This guide assumes you already have a working Maelstrom app. It stays on the integrator path the demo uses: browser packages and React ownership on one side, a backend `@maelstrom-co/voice-server` runtime on the other.

If you want the why behind that split, read [Voice Architecture](/understanding/voice-architecture/). If this is your first voice setup, start with [Add Voice Control](/tutorials/voice-control/).

## What this guide decides

Use this page after the first end to end setup already works. It focuses on the integration decisions the demo makes in real app shells:

1. where the one owning `m.useVoice({...})` call lives
2. how the shell keeps voice status, typed fallback, and retry UI together
3. when to start immediately, when to wait for a click, and when to degrade to typed or manual control
4. which session options are worth changing early, and which backend/runtime details should stay linked out

## Own the session with `m.useVoice({...})`

Keep one owner component near the app shell. That component creates the session, chooses the setup options, and renders the visible voice status.

```tsx
function DemoApp() {
  const voice = m.useVoice({
    autoAcquireMic: true,
    allowBargeIn: true,
    vadOptions: {
      minSpeechDurationSeconds: 0.032,
      preSpeechPaddingSeconds: 0.45,
    },
    greeting:
      "Hello! I'm the Maelstrom demo assistant. I can help you manage your calendar, weather, journal, and tasks. Try asking me to rearrange your dashboard or perform actions like adding tasks or writing journal entries.",
  });

  return (
    <div className="h-screen flex flex-col">
      <header className="bg-gray-800 border-b border-gray-700 px-6 py-4">
        <div className="flex items-center justify-between">
          <div>
            <h1 className="text-xl font-bold text-white">Maelstrom Demo</h1>
            <p className="text-sm text-gray-400">AI-Orchestrated Dynamic UI</p>
          </div>

          <div className="flex items-center gap-3">
            <m.VoiceOrb size={40} />
            <StatusIndicator />
          </div>
        </div>
      </header>

      <main className="flex-1 relative">
        <m.Chart />
      </main>

      <IntentInput />

      {voice.needsUserGesture && (
        <EnableVoiceDialog
          onEnable={() => {
            void voice.start();
          }}
          voiceState={voice.state}
        />
      )}
    </div>
  );
}
```

This is the demo's core ownership shape. The same component owns the session, surfaces status, and keeps the typed fallback in reach.

### One owner, many observers

Pass options in one place only. `m.useVoice({...})` creates the owner session. `m.useVoice()` with no options is the observer path for any other component that just needs shared state or actions.

That rule keeps microphone state, startup behavior, and error handling easy to reason about.

## Keep `m.VoiceOrb` and typed input in the same shell

The orb gives users visible feedback for shared states such as listening, speaking, and error.

```tsx
<div className="flex items-center gap-3">
  <m.VoiceOrb size={40} />
  <StatusIndicator />
</div>
```

Keep the typed path too. The demo leaves its text input in place after voice is enabled.

```tsx
function IntentInput() {
  const [intent, setIntent] = useState('');
  const { processIntent, isProcessing } = m.useMaelstrom();

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    if (!intent.trim() || isProcessing) return;

    await processIntent(intent);
    setIntent('');
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="text"
        value={intent}
        onChange={(e) => setIntent(e.target.value)}
        placeholder="Tell Maelstrom what you want to do..."
        disabled={isProcessing}
      />
      <button type="submit" disabled={isProcessing || !intent.trim()}>
        {isProcessing ? 'Processing...' : 'Send'}
      </button>
    </form>
  );
}
```

That is the safest default for most products. Voice adds another control path, it does not need to replace text input. If you want the full first-run shell walkthrough, use [Add Voice Control](/tutorials/voice-control/).

## Handle `needsUserGesture` with a real retry path

Browsers often block microphone access or playback until the user clicks something first. In Maelstrom, that shows up as `needsUserGesture`.

Render a real affordance when that flag flips to `true`:

```tsx
{voice.needsUserGesture && (
  <EnableVoiceDialog
    onEnable={() => {
      void voice.start();
    }}
    voiceState={voice.state}
  />
)}
```

Do not treat this as a decorative modal. The recovery UI should do three jobs:

1. explain that the browser needs a user click before the app can use the microphone and playback
2. reuse the same button for first enable and retry after a failed start
3. keep the typed path visible so the user can continue if permission or startup fails again

If you want to unlock audio without starting capture yet, call `voice.prepareAudio()` from the click handler instead. Use `voice.start()` when the same click should begin listening right away.

## Common session choices

You do not need the whole option surface to ship the first integration. These are the choices most apps make up front:

### `autoAcquireMic`

- Use `true` when your UI already has a clear gesture recovery path, like the demo dialog.
- Use `false` when you want the app to wait for an explicit start action.

### `greeting`

`greeting` fits the auto-start path. Keep it for flows where the app should speak as part of startup, not for delayed manual start.

### `allowBargeIn`

Set this to `true` when users should be able to interrupt assistant speech by talking. Leave it `false` when your product needs stricter turn-taking.

### `vadOptions`

Start with small overrides only. The demo changes just two fields:

- `minSpeechDurationSeconds: 0.032`
- `preSpeechPaddingSeconds: 0.45`

For deeper tuning, read [VAD Configuration](/guides/voice/vad-configuration/). For the full hook option surface, read [`UseVoiceOptions`](/reference/react-voice/type-aliases/usevoiceoptions/).

## Language, errors, and backend runtime settings

Browser session language belongs in `m.useVoice({...})`:

```tsx
const voice = m.useVoice({
  autoAcquireMic: true,
  language: 'es-ES',
});
```

Keep the rest of the boundary clean. Backend provider configuration, runtime timing, and speech queue behavior belong on the backend runtime pages, not in this guide. Detailed error semantics live on the dedicated error page.

Handle runtime failures in the owner component. Surface the failure near the voice controls, keep the retry path available, and fall back to typed or manual input when the browser voice path is not reliable enough for that device or room.
