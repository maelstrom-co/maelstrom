Use this guide when you already have a Maelstrom app and want to add the same voice flow the demo uses.

Voice integration has two halves:

- in the browser, `@maelstrom-co/react-voice` and `@maelstrom-co/voice` handle microphone capture, local Voice Activity Detection (VAD), playback, and the shared React session
- on the backend, `@maelstrom-co/voice-server` handles Speech-to-Text (STT), the handoff into the engine, Text-to-Speech (TTS), and speech delivery rules

You need both halves. The React package gives you a browser voice client, but it does not turn finalized speech into `ChartRequest`s or synthesize the assistant reply on its own.

If you want the rationale behind that split, read [Voice Architecture](/understanding/voice-architecture/). This page stays on the practical integration path.

<Aside type="tip">
  First time implementing voice? Follow [Add Voice Control](/tutorials/voice-control/) for the guided step-by-step path.
</Aside>

<Aside type="note">
  Voice is currently **React-only**. These snippets use the `@maelstrom-co/react-voice`
  bindings (`m.useVoice()`, `m.VoiceOrb`) and don't change with the framework selector —
  there's no Vanilla JS equivalent yet.
</Aside>

## What you'll wire up

By the end of this guide, your existing app will follow the same shape as the demo:

1. install `@maelstrom-co/react-voice` and `@maelstrom-co/voice`
2. extend your typed Maelstrom instance with `.with(maelstromVoice())`
3. provide a connector that supports the `voice` capability and streams to your backend runtime
4. keep one owning `m.useVoice({...})` call near the app shell
5. render `<m.VoiceOrb />` and keep typed input available
6. recover from `needsUserGesture` with a real click path

## 1. Install the browser packages

Add the browser voice packages to the app that already hosts your Maelstrom UI.

`@maelstrom-co/react-voice` dynamically loads the browser runtime from `@maelstrom-co/voice`, but `@maelstrom-co/voice` is still a peer dependency and should be installed explicitly, especially for npm, pnpm, and yarn workflows. Keep `@maelstrom-co/voice-server` on the server side, not in the browser bundle.

For package-level runtime notes, see [`packages/voice/README.md`](https://github.com/maelstrom-co/maelstrom/blob/main/packages/voice/README.md).

## 2. Extend your Maelstrom instance

The extension point is `maelstromVoice()`. Apply it once when you create the typed Maelstrom instance.

```tsx
import { createMaelstrom } from '@maelstrom-co/react';
import { maelstromVoice } from '@maelstrom-co/react-voice';
import { calendarEntry } from '../vessels/calendar.vessel';
import { journalEntry } from '../vessels/journal.vessel';
import { tasksEntry } from '../vessels/tasks.vessel';
import { weatherEntry } from '../vessels/weather.vessel';

export const m = createMaelstrom({
  vessels: [calendarEntry, weatherEntry, journalEntry, tasksEntry],
}).with(maelstromVoice());
```

That adds two browser-facing members to the instance:

- `m.useVoice()`, the shared session hook
- `m.VoiceOrb`, the visual state indicator

Only apply `maelstromVoice()` once per instance. The extension creates a shared voice store, so stacking it more than once creates separate stores and confusing ownership.

## 3. Provide a connector that actually supports voice

The voice extension does not create transport on its own. Your `m.Provider` still needs a connector that advertises the `voice` capability and forwards browser audio to your backend runtime.

The demo does that before any voice hook runs:

```tsx
function HomePage() {
  const connector = useMemo(() => createDemoConnector(), []);

  return (
    <m.Provider connector={connector} debug>
      <DemoApp />
    </m.Provider>
  );
}
```

In your app, that connector is the boundary between the browser session and the server runtime. Keep the boundary simple: the browser session streams audio through the connector, and the backend runtime does the STT, intent handoff, and TTS work.

For a demo-style setup, that voice-capable connector will typically use a WebSocket (WS) transport and stream linear16 Pulse-Code Modulation (PCM) audio chunks from the browser to the backend while the user is talking. That is a common shape, not the only valid transport. The contract that matters here is that the connector supports voice and carries the browser session audio to your backend runtime.

For backend setup details, use the dedicated docs:

- [`createVoiceSession()`](/reference/voice-server/functions/createvoicesession/)
- [Voice Server API Reference](/reference/voice-server/)
- [Voice Architecture](/understanding/voice-architecture/)

## 4. Own the session with `m.useVoice({...})`

Keep one owner component near the app shell. That component creates the session, chooses the setup options, and renders the visible voice status.

```tsx
function DemoApp() {
  const voice = m.useVoice({
    autoAcquireMic: true,
    allowBargeIn: true,
    vadOptions: {
      minSpeechDurationSeconds: 0.032,
      preSpeechPaddingSeconds: 0.45,
    },
    greeting:
      "Hello! I'm the Maelstrom demo assistant. I can help you manage your calendar, weather, journal, and tasks. Try asking me to rearrange your dashboard or perform actions like adding tasks or writing journal entries.",
  });

  return (
    <div className="h-screen flex flex-col">
      <header className="bg-gray-800 border-b border-gray-700 px-6 py-4">
        <div className="flex items-center justify-between">
          <div>
            <h1 className="text-xl font-bold text-white">Maelstrom Demo</h1>
            <p className="text-sm text-gray-400">AI-Orchestrated Dynamic UI</p>
          </div>

          <div className="flex items-center gap-3">
            <m.VoiceOrb size={40} />
            <StatusIndicator />
          </div>
        </div>
      </header>

      <main className="flex-1 relative">
        <m.Chart />
      </main>

      <IntentInput />

      {voice.needsUserGesture && (
        <EnableVoiceDialog
          onEnable={() => {
            void voice.start();
          }}
          voiceState={voice.state}
        />
      )}
    </div>
  );
}
```

This is the demo's core ownership shape. The same component owns the session, surfaces status, and keeps the typed fallback in reach.

### One owner, many observers

Pass options in one place only. `m.useVoice({...})` creates the owner session. `m.useVoice()` with no options is the observer path for any other component that just needs shared state or actions.

That rule keeps microphone state, startup behavior, and error handling easy to reason about. If the connector does not support voice, the browser dependency fails to load, or microphone startup fails, surface that state through your UI and `onError`, then leave typed input usable.

## 5. Keep `m.VoiceOrb` and typed input in the same shell

The orb gives users visible feedback for shared states such as listening, speaking, and error.

```tsx
<div className="flex items-center gap-3">
  <m.VoiceOrb size={40} />
  <StatusIndicator />
</div>
```

Keep the typed path too. The demo leaves its text input in place after voice is enabled.

```tsx
function IntentInput() {
  const [intent, setIntent] = useState('');
  const { processIntent, isProcessing } = m.useMaelstrom();

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    if (!intent.trim() || isProcessing) return;

    await processIntent(intent);
    setIntent('');
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="text"
        value={intent}
        onChange={(e) => setIntent(e.target.value)}
        placeholder="Tell Maelstrom what you want to do..."
        disabled={isProcessing}
      />
      <button type="submit" disabled={isProcessing || !intent.trim()}>
        {isProcessing ? 'Processing...' : 'Send'}
      </button>
    </form>
  );
}
```

That is the safest default for most products. Voice adds another control path, it does not need to replace text input. Keeping text available is also the best user experience (UX) fallback when browser voice is not reliable for a device, room, or permission state. If you want the full first-run shell walkthrough, use [Add Voice Control](/tutorials/voice-control/).

## 6. Handle `needsUserGesture` with a real retry path

Browsers often block microphone access or playback until the user clicks something first. In Maelstrom, that shows up as `needsUserGesture`.

Render a real affordance when that flag flips to `true`:

```tsx
{voice.needsUserGesture && (
  <EnableVoiceDialog
    onEnable={() => {
      void voice.start();
    }}
    voiceState={voice.state}
  />
)}
```

Do not treat this as a decorative modal. The recovery UI should do three jobs:

1. explain that the browser needs a user click before the app can use the microphone and playback
2. reuse the same button for first enable and retry after a failed start
3. keep the typed path visible so the user can continue if permission or startup fails again

If you want to unlock audio without starting capture yet, call `voice.prepareAudio()` from the click handler instead. Use `voice.start()` when the same click should begin listening right away.

## 7. Common session choices

You do not need the whole option surface to ship the first integration. These are the choices most apps make up front:

### `autoAcquireMic`

- Use `true` when your UI already has a clear gesture recovery path, like the demo dialog.
- Use `false` when you want the app to wait for an explicit start action.

### `greeting`

`greeting` fits the auto-start path. Keep it for flows where the app should speak as part of startup, not for delayed manual start.

### `allowBargeIn`

Set this to `true` when users should be able to interrupt assistant speech by talking. Leave it `false` when your product needs stricter turn-taking.

### `vadOptions`

Start with small overrides only. The demo changes just two fields:

- `minSpeechDurationSeconds: 0.032`
- `preSpeechPaddingSeconds: 0.45`

For deeper tuning, read [VAD Configuration](/guides/voice/vad-configuration/). For the full hook option surface, read [`UseVoiceOptions`](/reference/react-voice/type-aliases/usevoiceoptions/).

## 8. Keep language in the browser, keep runtime settings on the backend

`m.useVoice({ language })` sets the browser `VoiceSession` language that is forwarded through the connector and into your backend path. If you omit it, the browser session defaults to `'en'`.

Browser session language belongs in `m.useVoice({...})`:

```tsx
const voice = m.useVoice({
  autoAcquireMic: true,
  language: 'es-ES',
});
```

That setting does not replace backend runtime configuration. The backend voice session also has its own `language?: string` used for STT and TTS, and each provider can still apply its own defaults or supported options.

For a single-language flow, keep the browser session language, backend session language, STT language, and TTS language aligned. You can intentionally split them for translation flows or for language-specific voice choices, but that is a backend runtime decision, not something `m.useVoice({ language })` solves by itself.

Keep the rest of the boundary clean. Backend provider configuration, runtime timing, speech queue behavior, and provider-specific language defaults belong on the backend runtime pages, not in this guide. Detailed error semantics live on the dedicated error page.

Handle runtime failures in the owner component. Surface the failure near the voice controls, keep the retry path available, and fall back to typed or manual input when the browser voice path is not reliable enough for that device or room.
