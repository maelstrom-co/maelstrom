title: Architecture Overview
description: How Maelstrom's packages and layers fit together.

Maelstrom is organized as a layered architecture because the UI, protocol, engine, and voice runtime fail in different ways and need different deployment boundaries. Browser packages render and capture input; server packages own LLM, STT, and TTS provider calls; the protocol keeps the two sides speaking one contract.

```
@maelstrom-co/protocol    (foundation: shared types, zod schemas, message contract)
         │
    ┌────┴────┐
    ▼         ▼
@maelstrom-co/client   @maelstrom-co/engine
(framework-agnostic)   (LLM decision core)
    │
    ├────────────┐
    ▼            ▼
@maelstrom-co/react  @maelstrom-co/voice
(React bindings)     (audio capture/playback, VAD)
    │                    │
    └─────┬──────────────┘
          ▼
@maelstrom-co/react-voice
(React voice extension)

@maelstrom-co/voice-server
(backend STT, engine handoff, TTS runtime)
```

## Package responsibilities

| Package | Layer | Responsibility |
|---------|-------|---------------|
| `protocol` | Foundation | Types, Zod schemas, message definitions. Transport-agnostic. |
| `client` | Client | Orchestrator, ChartManager, CommandProcessor, VesselManager, connectors. Framework-agnostic. |
| `react` | UI | React bindings — `createMaelstrom()`, `vessel()`, Provider, Chart, hooks. |
| `engine` | Server | LLM decision engine — processes context and returns execution plans. |
| `voice` | Client (optional) | Audio capture, playback, VAD (Silero via onnxruntime-web). |
| `react-voice` | UI extension (optional) | React `useVoice()` and `VoiceOrb` integration on a Maelstrom instance. |
| `voice-server` | Server (optional) | STT, engine handoff, TTS, speech queueing, and runtime voice lifecycle. |

## Client architecture

The client uses a **microkernel architecture**. The `Orchestrator` is the composition root that coordinates independent managers:

- **ConnectionManager** — Manages transport lifecycle, reconnection, circuit breaking
- **VesselManager** — Tracks registered vessels and their current state
- **ChartManager** — Manages grid dimensions and layout computation
- **CommandProcessor** — Event loop that processes layout and action commands
- **RequestCoordinator** — Coordinates request/response pairs with the engine

Each manager owns a TanStack Store for reactive state and extends TypedEmitter for events.

## Voice (optional)

Maelstrom also ships an optional full-stack voice layer. See [Voice Architecture](/understanding/voice-architecture/) for how the browser audio pipeline, client VAD, and server runtime connect.

## Data flow

1. User expresses intent (text or voice)
2. Client packages intent + context into a `ChartRequest`
3. `ChartRequest` is sent to the Engine via a connector
4. Engine processes with LLM and returns a `MaelstromResponse`
5. Client executes actions, reads the resulting variant sizes, applies layout, then handles overflow

The order in step 5 is load-bearing. Layout must happen after actions because actions can transition Vessels into variants with different `minSize` requirements.
