## Overview

Maelstrom's voice stack is intentionally split across two runtimes because the browser and the server are good at different jobs. The browser owns microphone capture, local Voice Activity Detection, playback, and the live WebSocket session. The server owns the speech-to-text provider, the handoff into the Maelstrom engine, the text-to-speech provider, and the rules for queued or interrupted speech.

That split matters because end-to-end voice needs both halves. `@maelstrom-co/react-voice` and `@maelstrom-co/voice` give you a real browser voice client, but they do not turn transcripts into `ChartRequest`s or synthesize assistant replies by themselves. `@maelstrom-co/voice-server` closes that loop. The demo app is the reference integration because it wires the whole path together without hiding the seams.

## Package Boundaries

Maelstrom exposes voice through three packages with deliberately different responsibilities.

### `@maelstrom-co/react-voice`

This is the React-facing layer. You attach it to a Maelstrom instance with `.with(maelstromVoice())`, then consume the shared session through `m.useVoice()` and render state with `<m.VoiceOrb />`.

That extension exists so React apps can stay declarative while the lower-level voice runtime stays framework-agnostic. The extension also does an SSR-safe dynamic import of `@maelstrom-co/voice`. On the server it skips the browser-only probe, which avoids pulling `onnxruntime-web` into server-side module evaluation.

### `@maelstrom-co/voice`

This is the browser runtime. It owns audio capture, audio playback, VAD, the WebSocket connector, and the `VoiceSession` state machine. The user-facing states are intentionally small: `idle`, `listening`, `silence`, `speaking`, and `error`.

The important boundary here is that `@maelstrom-co/voice` is still client-side infrastructure. It can detect speech, stream PCM audio, react to transcripts, and interrupt playback, but it does not decide how a finalized transcript becomes a Maelstrom intent request. That boundary stays on the server.

### `@maelstrom-co/voice-server`

This is the backend runtime that turns browser voice events into a complete conversational loop. It owns STT and TTS provider registries, the `ProcessIntent` contract, speech queuing, reconnect policy, transcript grace handling, and per-session lifecycle management.

The core contract is intentionally small: the runtime receives finalized speech, calls `buildChartRequest`, passes that request to `processIntent`, then decides how and when to speak the resulting reply. That keeps the voice runtime engine-agnostic while still integrating cleanly with Maelstrom's response pipeline.

## Data Flow

The full path is easier to understand as a turn lifecycle.

1. The browser captures microphone audio and feeds it through local VAD.
2. Once VAD decides the user is speaking, the browser starts sending PCM chunks over WebSocket to the server runtime.
3. The server forwards those chunks to the configured STT provider and receives interim or final transcript updates.
4. When the transcript is final enough to count as a turn, the runtime calls `buildChartRequest`, then hands the request to `ProcessIntent`, which returns a `MaelstromResponse`.
5. The runtime extracts the user-facing reply text and sends it to the configured TTS provider.
6. The TTS provider streams audio chunks back through WebSocket to the browser.
7. The browser plays the audio and updates session state to `speaking`.
8. If the user speaks again during playback, local VAD fires, the session interrupts active speech, and the runtime moves back toward listening for the new turn.

That last step is what makes barge-in feel reliable. The interruption logic lives in the session state machine, not inside an STT or TTS provider. Providers generate media. The runtime decides turn ownership.

## Client-Owned VAD

One of the most opinionated parts of the stack is that VAD runs in the browser. Maelstrom uses the Silero model through ONNX Runtime Web and Wasm, so utterance-boundary decisions happen locally before audio-provider heuristics get the final word.

The reason is consistency. STT providers differ a lot in how they treat silence, slow speakers, and partial transcripts. Some are aggressive about splitting turns. Others wait too long. Some can hallucinate extra utterances on slower voices unless you tune silence thresholds very carefully. If the product delegates turn boundaries entirely to the provider, the UX starts to drift every time you swap STT backends or even change the pacing of the same user's speech.

Client-owned VAD gives Maelstrom a stable boundary layer above those quirks. The browser decides when speech starts and when it probably ended. The server still gives the STT provider a brief chance to flush a better final transcript, but the product-level turn shape is no longer owned by a provider-specific silence heuristic.

There is also an acoustic echo cancellation caveat. During TTS playback the VAD activation threshold is raised so leaked speaker output is less likely to retrigger the microphone path. That helps preserve barge-in without treating the assistant's own voice as a fresh user turn. If browser AEC is weak or unavailable, false positives are still possible, so this is a mitigation, not magic.

This design has real costs. The Silero model adds roughly 2 MB to first-use browser download size, it requires Wasm support, and inference adds roughly 10 to 30 ms to turn detection. That's a fair price for consistent cross-provider control, but it is still a price.

## Provider Registries and error taxonomy

The server runtime treats providers as discriminated configuration objects instead of ad hoc constructor calls. STT is selected with configs such as `{ type: 'deepgram', options: ... }` or `{ type: 'google', options: ... }`. TTS follows the same shape.

Today that means:

- STT providers: `deepgram`, `google`
- TTS providers: `cartesia`

This is a practical design choice more than an aesthetic one. The registry keeps provider selection explicit, validates the public config shape in one place, and lets the runtime specialize STT and TTS independently. You can pick the recognizer and the synthesizer that fit your latency, quality, or pricing needs without pretending they have to come from the same vendor.

Errors are normalized the same way. The runtime classifies provider failures into a coarse taxonomy: `auth`, `quota`, `transport`, `parse`, `server`, and `unknown`. That taxonomy crosses the WebSocket boundary instead of raw provider error objects.

The benefit is boring but important. Client code can render one consistent error surface regardless of whether the failure came from Deepgram, Cartesia, or Google. It also keeps vendor-specific error shapes from leaking into your browser contract. The tradeoff is reduced precision. The taxonomy is intentionally coarse, so some provider nuance is flattened on purpose.

## Transcript Grace and Turn Boundaries

Not every finalized turn arrives cleanly on the first try. Some STT providers will emit a quick interim transcript, then upgrade it moments later with a better final version. If the runtime hands control to the engine too early, you get clipped or lower-quality user turns.

That is what `transcriptGraceMs` is for. After VAD says a turn ended, the server runtime can wait briefly for the STT provider to deliver the better final transcript before the request goes to the engine. This is a server-side turn-quality knob, not a browser VAD field.

`vadFinalDebounceMs` solves a different problem. It smooths out tiny silence gaps that happen inside what humans would still call one utterance. Without that debounce, short pauses between phrases can prematurely end a turn.

Both fields live in `VoiceSessionConfig` on the server because they tune runtime handoff behavior after browser VAD has already done its job. The browser decides speech boundaries locally. The server decides how cautiously to treat the trailing edge of that boundary before committing to intent processing.

## Speech Queue and Agent Speech

The runtime has two different speech semantics because not all output should behave the same way.

`voiceSession.speak()` has replacement semantics. It immediately supersedes active speech and clears queued output. Use it when the new message matters more than anything currently being spoken.

`voiceSession.enqueueSpeak()` has queue semantics. It appends speech behind the current utterance and lets playback continue in order.

That distinction matters for assistant replies. Longer responses are often more stable when delivered sentence by sentence through the queue instead of as one giant replacement call that risks clipping mid-turn if something interrupts. It also matters for agent and tool speech. Tool-originated TTS is output-only. It uses the queued path and does not need to own the microphone, which keeps spoken notifications and assistant replies from being coupled to browser capture state.

## Runtime Decomposition

The server runtime is deliberately decomposed into smaller coordinators instead of one monolithic voice loop. There is separate logic for STT transport, TTS session management, VAD coordination, turn coordination, buffering, and event emission.

That decomposition is not just about code style. Voice systems fail in awkward, stateful ways. A reconnecting STT transport, an interrupted TTS stream, a delayed final transcript, and a queued speech response are all different failure modes. Smaller runtime units make it easier to test those paths independently and easier to reason about who owns each transition.

The drawback is complexity at the package level. There are more moving parts to learn, and a complete voice setup requires both browser and server infrastructure. The upside is that the failure boundaries are clearer, which matters more here than having a superficially tiny implementation.

## Benefits and Drawbacks

### Benefits

- Consistent utterance-boundary control across STT providers because VAD is owned on the client.
- Provider specialization, so STT and TTS can be chosen independently instead of as a forced bundle.
- Reliable barge-in because interruption lives in the session state machine, not in provider-specific behavior.
- Cleaner testing boundaries because browser capture, runtime coordination, engine handoff, and speech synthesis are separated.
- A stable browser contract because provider errors are normalized before they cross the WebSocket boundary.

### Drawbacks

- Roughly 2 MB of ONNX model download on first use, plus a Wasm requirement in the browser.
- End-to-end voice requires a deployed `@maelstrom-co/voice-server`, not just the client packages.
- Latency is chained across STT, engine processing, and TTS, so each stage adds to turn completion time.
- Provider credentials must stay server-side, which means a real voice integration always needs backend infrastructure.
- The split architecture is easier to test, but it is also more operationally involved than a single-package toy demo.
